## Context

この変更では、単一画面の Todo 管理機能とブラウザ内での永続化を新たに追加する。動機と利用者向けの振る舞いは proposal.md および `specs/todo-management/spec.md` を参照する。学習目的のため、状態管理の仕組みは React の基本機能に限定する。

## Goals / Non-Goals

**Goals:**

- Todo のタイトル、完了状態、識別子を持つ小さなデータモデルをクライアント側で扱う。
- 初回に localStorage から一覧を読み込み、一覧が変化したときに保存する。
- 画面上の操作を、追加・完了切替・削除に限定して分かりやすく保つ。

**Non-Goals:**

- サーバー同期、ユーザー認証、複数端末間共有を実現しない。
- Todo の編集、フィルタリング、期限、優先度を追加しない。
- 状態管理ライブラリ、コンテキスト、`useReducer` を導入しない。

## Decisions

### `useState` を唯一のアプリケーション状態として使う

Todo 一覧は `useState` で保持し、追加・切替・削除では新しい配列を作成して更新する。これは状態遷移をコンポーネント内で追いやすくし、学習範囲を React の基本に絞れるためである。

代替案として `useReducer` や外部ストアがあるが、操作数が少なく、今回の学習目的には過剰なため採用しない。

### localStorage を状態の復元元と保存先にする

状態の初期化時に localStorage から保存済みの Todo 一覧を読み取り、Todo 一覧が変化した後に JSON として保存する。これによりページ再読み込み後もデータを維持できる。

代替案のインメモリ状態のみでは再読み込みで失われ、バックエンドを使う案は最小構成の範囲を超えるため採用しない。

### 不正または読み取れない保存値は空の一覧として扱う

localStorage に値がない、または JSON として解釈できない場合は、アプリを利用可能に保つため空の一覧から開始する。

代替案として読み込みエラーを画面に表示する方法があるが、保存データを利用者が直接管理しない最小アプリでは操作を増やすため採用しない。

## Risks / Trade-offs

- [ブラウザのストレージを消去すると Todo も失われる] → 保存先が端末内に限られることを前提とし、同期機能は追加しない。
- [異なるブラウザや端末では一覧を共有できない] → 学習目的の最小構成として受け入れる。
- [localStorage の内容が壊れる可能性がある] → 読み込みに失敗した場合は空の一覧にフォールバックする。

## Migration Plan

新規機能のため既存データの移行は不要である。問題が発生した場合は、アプリを以前のバージョンへ戻し、必要に応じて該当の localStorage キーを削除して空の一覧から再開する。
